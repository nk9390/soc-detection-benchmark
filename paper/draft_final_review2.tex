\begin{abstract}
Security Operations Centers rely on detection rules to identify malicious activity, yet systematic evaluation of rule efficacy remains challenging. We present a reproducible benchmark framework that measures detection rule performance against simulated attack behaviors mapped to MITRE ATT\&CK. Using a containerized lab environment with Atomic Red Team tests, we evaluate true positive rate, mean time to detect, and alert volume using \textbf{keyword-based Elasticsearch queries} (not compiled Sigma rules).

\textbf{Status:} This draft reports results from a single-technique validation (T1136.001 - Local Account Creation). The \textbf{validated} technique achieved 100\% detection rate with a mean time to detect of 3.20 seconds. One additional technique (T1053.003) now has telemetry enabled but is \textbf{not yet validated}. The remaining 9 techniques require auditd, which is unavailable in Docker.

\textbf{Limitation:} The containerized target environment cannot run \texttt{auditd} due to kernel restrictions. False positive rate measurement requires a baseline workload run, which has not been performed.
\end{abstract}

\section{Introduction}

Detection engineering is a critical discipline within security operations, yet practitioners lack standardized methods for evaluating detection rule effectiveness. Questions such as ``What percentage of attacks do our rules detect?'' and ``How many false positives do our rules generate?'' often go unanswered due to the absence of systematic benchmarking approaches.

This paper presents a reproducible framework for evaluating detection rules against simulated attack behaviors. Our contributions include:

\begin{itemize}
    \item A containerized lab environment for reproducible experiments
    \item A benchmark harness that executes ATT\&CK-mapped attacks and measures detection metrics
    \item \textbf{Validated} detection of T1136.001 (Local Account Creation) via auth.log
    \item Systematic telemetry gap analysis for 10 additional techniques
    \item Fully open-source artifacts for reproducibility
\end{itemize}

\textbf{Scope clarification:} This implementation uses keyword-based Elasticsearch queries, not compiled Sigma rules. False positive rate measurement is supported by the framework but was not performed in this validation run.

\section{Methodology}

\subsection{Lab Architecture}

Our benchmark uses a Docker Compose stack with four components:

\begin{enumerate}
    \item \textbf{Target Container}: Ubuntu 22.04 with rsyslog logging and Atomic Red Team
    \item \textbf{Log Shipper}: Filebeat shipping logs to Elasticsearch
    \item \textbf{Detection Engine}: Elasticsearch with keyword-based detection queries
    \item \textbf{Benchmark Harness}: Python orchestration for test execution and metrics collection
\end{enumerate}

\subsection{Log Source Limitations}

\textbf{Critical telemetry constraint:}

The Linux audit subsystem (\texttt{auditd}) cannot operate within Docker containers due to kernel-level restrictions:

\begin{verbatim}
auditd: Error setting audit daemon pid (Operation not permitted)
auditd: The audit daemon is exiting.
\end{verbatim}

\textbf{Functional log sources:}
\begin{itemize}
    \item \texttt{/var/log/auth.log} --- Authentication events (\texttt{useradd}, \texttt{userdel})
    \item \texttt{/var/log/cron.log} --- Cron events (telemetry now enabled; requires manual setup)
\end{itemize}

\subsection{Detection Method}

The current implementation uses keyword-based detection via Elasticsearch queries:

\begin{lstlisting}[language=json,caption={Detection Query for T1136.001}]
{
  "bool": {
    "must": [
      {"range": {"@timestamp": {"gte": "...", "lte": "..."}}},
      {"bool": {
        "should": [
          {"match": {"message": "user_add"}},
          {"match": {"message": "user_mod"}},
          {"match": {"message": "useradd"}}
        ],
        "minimum_should_match": 1
      }}
    ]
  }
}
\end{lstlisting}

\textbf{Note:} This is \textbf{not} a Sigma rule evaluation. The benchmark does not use sigma-cli or Sigma rule compilation. Future work could add Sigma support.

\subsection{Collection Window}

The benchmark queries for alerts within a time window around each attack:
\begin{itemize}
    \item \textbf{Pre-attack buffer}: 1 second before attack start
    \item \textbf{Post-attack buffer}: 15 seconds after attack end (accounts for Filebeat ingestion latency)
\end{itemize}

\subsection{Metrics}

We measure the following metrics:

\begin{itemize}
    \item \textbf{True Positive Rate (TPR)}: $\frac{\text{Attacks Detected}}{\text{Total Attacks}}$
    \item \textbf{False Negative Count}: Attacks with no matching alert
    \item \textbf{Mean Time to Detect (MTTD)}: Latency from attack execution to alert timestamp
    \item \textbf{Alert Volume}: Alerts generated per attack
\end{itemize}

\textbf{Not measured in this run:}
\begin{itemize}
    \item \textbf{False Positive Rate}: Requires a baseline workload run (framework supports this but not executed)
\end{itemize}

\section{Limitations}

\begin{itemize}
    \item \textbf{auditd unavailable}: The containerized environment cannot run the Linux audit subsystem, blocking 9 of 11 planned techniques
    \item \textbf{Single technique validated}: Only T1136.001 has been tested end-to-end
    \item \textbf{Keyword matching only}: Detection uses keyword queries rather than compiled Sigma rules
    \item \textbf{No FP measurement}: False positive rate requires baseline workload run (not performed)
    \item \textbf{Linux-only}: No Windows coverage
    \item \textbf{Single SIEM backend}: Elasticsearch only
    \item \textbf{Temporary cron setup}: T1053.003 telemetry requires manual enablement per container lifecycle
\end{itemize}

\section{Conclusion}

We validated the detection pipeline for T1136.001 (Local Account Creation), achieving 100\% detection rate with 3.20-second mean time to detect using keyword-based Elasticsearch queries.

\textbf{Key findings:}
\begin{enumerate}
    \item \textbf{1 technique validated}: T1136.001 --- 100\% detection via auth.log
    \item \textbf{1 technique now detectable}: T1053.003 --- cron telemetry enabled, awaiting validation
    \item \textbf{9 techniques blocked}: Require auditd unavailable in Docker
\end{enumerate}

\textbf{Distinction:} ``Validated'' means end-to-end test confirmed detection. ``Detectable'' means telemetry exists but attack not yet run.

Full benchmark coverage requires either:
\begin{enumerate}
    \item A VM-based environment where auditd can operate, or
    \item Permanent cron enablement in Dockerfile/entrypoint.sh, or
    \item Scope reduction to auth.log/cron.log techniques
\end{enumerate}
