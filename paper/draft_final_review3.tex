\begin{abstract}
Security Operations Centers rely on detection rules to identify malicious activity, yet systematic evaluation of rule efficacy remains challenging. We present a reproducible benchmark framework that measures detection rule performance against simulated attack behaviors mapped to MITRE ATT\&CK. Using a containerized lab environment, we evaluate true positive rate and mean time to detect using \textbf{keyword-based Elasticsearch queries}.

\textbf{Results:} Of 11 planned techniques, 2 were validated end-to-end:
\begin{itemize}
    \item T1136.001 (Local Account): 100\% detection, 3.20s TTD
    \item T1053.003 (Cron): 100\% detection, 30.94s TTD (requires 65s collection window)
\end{itemize}

The remaining 9 techniques require \texttt{auditd} syscall logging, which is unavailable in Docker containers due to kernel restrictions.

\textbf{Scope:} This benchmark uses keyword matching against log messages, not compiled Sigma rules. False positive rate measurement was not performed.
\end{abstract}

\section{Introduction}

Detection engineering is a critical discipline within security operations, yet practitioners lack standardized methods for evaluating detection rule effectiveness. This paper presents a reproducible framework for evaluating detection rules against simulated attack behaviors.

\subsection{Contributions}

\begin{itemize}
    \item A containerized lab environment for reproducible experiments
    \item A benchmark harness that executes ATT\&CK-mapped attacks
    \item Technique-specific collection windows for delayed telemetry
    \item Two validated technique detections with measured TTD
    \item Systematic telemetry gap analysis for 9 blocked techniques
    \item 60 automated regression tests
\end{itemize}

\subsection{Scope Clarification}

This implementation uses \textbf{keyword-based Elasticsearch queries}, not a Sigma rule engine. The detection approach searches for technique-specific keywords in log messages within a time window around each attack. This is simpler than full Sigma rule evaluation but sufficient for measuring detection pipeline performance.

\section{Methodology}

\subsection{Lab Architecture}

The benchmark uses a Docker Compose stack:

\begin{enumerate}
    \item \textbf{Target Container}: Ubuntu 22.04 with rsyslog and cron
    \item \textbf{Log Shipper}: Filebeat 8.12.0
    \item \textbf{Detection Engine}: Elasticsearch 8.12.0 with keyword queries
    \item \textbf{Benchmark Harness}: Python orchestration
\end{enumerate}

\subsection{Collection Windows}

The benchmark uses technique-specific post-attack buffers:

\begin{itemize}
    \item \textbf{Default}: 15 seconds (covers Filebeat ingestion latency)
    \item \textbf{T1053.003 (Cron)}: 65 seconds (cron checks crontab at minute boundaries)
\end{itemize}

The extended cron window accounts for:
\begin{enumerate}
    \item Event generation delay: cron daemon checks for changes at :01 each minute
    \item Worst-case delay: attack at :02 won't be detected until :01 of next minute (59s)
    \item Ingestion latency: ~5s for Filebeat to index the event
\end{enumerate}

\subsection{Detection Method}

For each technique, detection uses keyword matching:

\begin{lstlisting}[language=json,caption={Example: T1136.001 Detection Query}]
{
  "bool": {
    "must": [
      {"range": {"@timestamp": {"gte": "start", "lte": "end"}}},
      {"bool": {
        "should": [
          {"match": {"message": "user_add"}},
          {"match": {"message": "user_mod"}},
          {"match": {"message": "useradd"}}
        ],
        "minimum_should_match": 1
      }}
    ]
  }
}
\end{lstlisting}

\subsection{Metrics}

\begin{itemize}
    \item \textbf{True Positive Rate}: $\frac{\text{Detected Attacks}}{\text{Executed Attacks}}$
    \item \textbf{Mean Time to Detect (TTD)}: First alert timestamp - attack start time
    \item \textbf{Alert Volume}: Number of matching events per attack
\end{itemize}

\section{Limitations}

\begin{enumerate}
    \item \textbf{auditd unavailable}: Docker kernel restrictions block 9 of 11 techniques
    \item \textbf{Keyword matching only}: Not a Sigma rule evaluation
    \item \textbf{No FP measurement}: Baseline workload not executed
    \item \textbf{Linux-only}: No Windows coverage
    \item \textbf{Cron telemetry manual}: Requires runtime setup (not persistent)
    \item \textbf{rsyslog compression}: Repeated identical messages may be compressed
    \item \textbf{Small sample}: Each technique tested once
\end{enumerate}

\section{Reproducibility}

\subsection{Environment}

\begin{itemize}
    \item Host: macOS (Darwin 27.0.0)
    \item Docker: Elasticsearch 8.12.0, Filebeat 8.12.0, Ubuntu 22.04
    \item Python: 3.13.5
\end{itemize}

\subsection{Commands}

\begin{lstlisting}[language=bash]
# Start lab
cd docker && docker-compose up -d

# Enable cron telemetry (required for T1053.003)
docker exec soc-target bash -c '
  sed -i "s/#cron.*/cron.*/" /etc/rsyslog.d/50-default.conf
  killall rsyslogd; rsyslogd
  service cron start'

# Run tests
python -m pytest tests/ -v

# Execute single technique
python -c "from benchmark.runner import AttackRunner; \\
  r = AttackRunner(); r.run_single_technique('T1136.001')"
\end{lstlisting}

\subsection{Test Suite}

60 automated tests covering:
\begin{itemize}
    \item Timestamp handling and UTC conversion
    \item Collection window buffers (default and technique-specific)
    \item Detection key matching
    \item Metrics calculation
    \item Attack result serialization
\end{itemize}

\section{Conclusion}

We validated detection for 2 of 11 ATT\&CK techniques in a Docker-based lab:
\begin{itemize}
    \item T1136.001: 3.20s TTD via auth.log
    \item T1053.003: 30.94s TTD via cron.log (requires extended collection window)
\end{itemize}

The remaining 9 techniques require auditd syscall logging, unavailable in Docker. Full coverage requires a VM-based environment.

The key engineering contribution is technique-specific collection windows, addressing the fundamental timing difference between immediate telemetry (auth.log) and delayed telemetry (cron's minute-boundary checks).
